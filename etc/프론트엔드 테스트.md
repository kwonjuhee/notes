## 테스트 대상

### 시각적 요소

- 컴포넌트가 실제로 렌더링되는 모습이 의도한대로 나타나는지 테스트
- 스냅샷 테스트 → Jest
- 시각적 회귀 테스트 (Visual Regression Test) → Chromatic

### 사용자 이벤트 처리

- 사용자의 입력 이벤트를 적절한 이벤트 핸들러로 처리하는지 시뮬레이션 테스트
- testing-library
- E2E 테스트

### API 서버 통신

- API client 모킹
- Jest
- msw
    - jest와 storybook에서 각각 api 모킹이 필요하다.
    - msw를 도입하여 api 모킹 작업을 한 번의 작업으로 처리할 수 있다.

1. **`button`** element가 제대로 mount 되는가?
2. **`props`**에 따라 className이 제대로 변경되는가?
3. **`props`**으로 전달한 값이 button element에 제대로 반영되는가?
4. 버튼을 클릭했을 때, **`click`** event가 제대로 동작하는가?

UI 검증을 위한 테스트는 변경에 자유로울 수 없다. UI는 언제든지 깨질 수 있다.

- 제대로 된 위치에 mount되더라도 부모 컴포넌트에 의해 UI가 깨질 수 있다.
- className이 제대로 변경되었다고 하더라도 스타일이 제대로 안들어갈 수 있다.
- children에 또다른 컴포넌트가 들어온다면

테스트는 어플리케이션을 사용할 때 의도한대로 동작하는 것에 확신을 갖기 위해 작성한다는 것을 명심하자.

### 동작에 집중하기

1~4번 중 사용자의 동작은 4번뿐이다. (사용자가 버튼을 클릭하는 행위)

그대로 테스트하지 않는다.

- 이벤트가 제대로 트리거되는지를 테스트하는 것은 플랫폼(브라우저, React)을 믿지 않는 것.
- 이벤트가 제대로 발생할지는 플랫폼을 믿자. 이 부분에 대한 단위테스트는 작성하지 않는다.

이벤트가 발생하여 어떠한 부수 효과(side effect)를 가져오는가를 테스트한다.

- 버튼을 클릭하여 발생하는 동작
- 예를 들면 컴포넌트 상태 변경/다른 페이지로 이동/오버레이 띄우기 등등
- 어플리케이션의 흐름(flow), 비즈니스 로직, 개발자가 어플리케이션 코드를 작성할때 의도한 동작에 해당된다.

부수 효과들이 발생하게 되는 조건과 결과를 테스트

## 테스트의 기본

- 테스트 케이스는 반드시 참, 거짓을 반환해야 한다.
- 참, 거짓은 반드시 어떠한 가정을 통해 포함한다.
- 이 가정에 따라 출력된 값이 예상한 값과 일치하는지에 따라 참, 거짓을 결정한다.
- 테스트의 결과는 외부 요소에 의해 결정되면 안되며 오로지 가정에 의해서만 결정되어야 한다.
- 가정이 변하지 않는 한 테스트의 결과는 항상 동일해야 한다.
- 가정은 테스트 케이스의 의도를 포함하며 각 테스트 케이스 하나 당 하나의 의도만을 포함해야 한다.

## 테스트 케이스 만들기

### Given-When-Then pattern

```jsx
test('should $1', () => {
  // Given
  const data = $4

  // When
  const result = $3

  // Then
  expect(result).toEqual($2)
})
```

1. 테스트 케이스의 목적을 작성한다.
2. 최종적으로 확인해야 하는 부분, 즉 예상하는 값을 작성한다.
    1. toEqual, toBe, toBeFalsy
3. 어떠한 flow를 검증할지 작성한다.
    1. 주어진(given) 데이터를 기반으로 어떠한 행동을 취했을 때 검증해야하는 값
    2. 어떠한 함수를 호출했을 때의 반환값이거나 결과
4. 3번 검증을 위해 어떤 가정이 필요한지 작성한다.
    1. 변수, payload, mocking하는 state object 등등

## 테스트 분류

### 단위 테스트 (Unit Test)

- 테스트 가능한 가장 작은 단위의 코드를 테스트하는 기법
- 독립적으로 참, 거짓을 판단하기 때문에 테스트가 실패했을 경우 어느 부분이 문제인지 빠르게 파악할 수 있다.
- 어플리케이션의 전체적인 플로우가 정상임을 보장하지 않는다.

### 통합 테스트 (Integration Test)

- 두 가지 이상의 요소가 함께 상호 작용할 때, 개발자가 의도한 대로 동작하는지 테스트하는 기법이다.
- store에 연결된 컴포넌트를 테스트하는 경우
- 이 또한 하나의 가정을 테스트

### E2E 테스트 (End-to-End Test)

- 기능 테스트(Functional Test)라고도 불리는 테스트 기법
- 사용자가 직접 어플리케이션을 사용하는 것처럼 동작하도록 스크립트를 작성하고 이것을 실행시켜보면서 기대한대로 동작하는지 검증할 수 있다.

## 테스트 비용

- 테스트 코드는 작성할 때 뿐만 아니라 운영중에 유지보수하는데에도 큰 비용이 들어간다.

## 비즈니스 로직과 UI 렌더링의 분리

- 테스트를 하기 전 비즈니스 설계가 제대로 되어야 한다.
- 컴포넌트에 비즈니스 로직이 들어가게 되면 그 부분은 테스트를 할 수 없게 되며 발생할 수 있는 버그로부터 안전하다는 것을 보장받을 수 없게 된다.
- 비즈니스 로직을 분리하여 관리하자.
    - 특정 버튼을 클릭하였을 때, 어떤 조건에 따라서 팝업이 노출해야 한다.
    - api 호출 시, 에러가 발생했을 때 알맞은 에러 메세지를 노출해야 한다.
    - 특정 조건에 따라 버튼이 활성화되고 비활성화된다.
- 예외
    - 사용자 동작에 대한 alert 띄우기
    - anchor 태그 클릭을 통한 외부 페이지로의 이동
    

## UI 검증을 위한 Storybook 활용

- 앞서 컴포넌트 렌더링에 대한 단위 테스트를 진행하지 않는다고 하였다.
- UI 깨짐은 쉽게 대응이 가능한 부분. UI가 깨진 특정 상황이 무엇인지 빠르게 파악할 수 있도록 도와주는 컴포넌트 시각화 도구 Storybook 활용
    - 만약 배포된 프로덕트에서 UI 버그가 발생한다면 버그가 발생한 화면의 스토리북을 우선적으로 확인하고 UI를 렌더링하는 로직에 문제가 없는지 먼저 확인할 수 있다.
    - 그 후 원인이 될 수 있는 영역을 좁혀나가면서 디버깅
- storybook은 주로 공통 컴포넌트를 관리하거나 디자인 시스템을 운영할 때 각각의 컴포넌트의 렌더링 상태를 확인하기 위해 사용된다.
- 페이지 단위로 스토리를 작성하여 store의 특정 상황에 대한 화면 렌더링 상태를 통째로 그려주어
    - 웹 페이지에 접근하는 비용을 줄일 수 있다.
    - 개발자가 직접  mock data를 대입해보거나 상호작용을 테스트해볼 필요가 없도록

## 여러 테스팅 방법에 대해 생각해보기

### snapshot 테스트

- 과연 올바른 피드백인가?
- 스냅샷이 왜 깨졌는지 살펴보고 디버깅하는 비용

### E2E 테스트

- 시나리오가 필요하다. 완벽한 어플리케이션 설계도를 포함하여 모든 케이스를 빠뜨리지 않고 시나리오를 작성해야 한다.
- 모든 api가 제대로 동작하고 실제 데이터와 유사한 데이터가 DB에 적재되는 것은 개발 단계에서 매우 어려운 일이다.
- 테스팅 시간이 오래걸린다. 따라서 별도의 관리 포인트가 생기게 된다.

## Test Coverage

- 테스트 코드가 커버하고 있는 프로덕션 코드의 정도를 측정한 값
- 이를 높이려고 테스트 코드를 작성하는 것은 주객전도 상황이다. 수치에 너무 연연하지 말자.
