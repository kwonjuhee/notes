# 프론트엔드 테스트

> 테스트란 **애플리케이션이 기대한 결과대로 동작하는지 검증**하는 일련의 모든 행위를 말한다. **애플리케이션의 안전성과 유지 보수성 향상**을 위한 행위이다.
> 
- 프론트엔드 애플리케이션은 대부분 사용자와의 인터랙션으로 애플리케이션의 상태가 변경되거나 비즈니스 로직이 실행된다. 그렇기 때문에 실제로 **`‘사용자 관점’`에서 최대한 사용자가 직접 사용하는 것처럼** **시나리오를 작성하여 검증**하는 것이 중요하다.
- DOM 요소들의 레이아웃이나 스타일이 적절하게 적용되었는지
- 애니메이션이 있다면 애니메이션이 올바르게 동작하는지

# 좋은 테스트

- **모든 테스트는 독립적으로 실행되어야 한다.**
    - 다른 테스트의 결과나 실행 여부와는 무관하게 독립적으로 실행되어야 한다. 다른 테스트의 결과에 따라 결과가 바뀌는 의존적인 테스트는 검증을 통과하더라도 결과를 신뢰할 수 없을 것이다.
- **테스트의 결과는 일관성이 있어야 한다.**
    - 테스트는 외부 환경에 상관 없이 일관성 있는 검증을 수행해야 한다. 적절한 모킹을 통해 테스트 환경의 OS, 네트워크 또는 다른 시스템과의 인터페이스 등 외부 의존성을 최소화 해야한다.
- **내부 구현에 종속된 테스트는 지양해야 한다.**
    - 외부 코드에서 내부 구현에 대해 많이 알고 있는 것은 모듈 간의 결합도를 높이고 캡슐화를 위반하기 때문에 유지 보수를 어렵게 만든다. 아주 작은 구현의 변경에도 테스트 코드가 깨지기 쉽기 때문이다. 이러한 테스트는 의미없는 테스트가 될 가능성이 높다.
    - 테스트 코드는 내부 구현보다는 인터페이스를 기준으로 테스트하는 것이 좋다.
- **테스트는 단순하고 이해하기 쉬워야 한다.**
    - 다른 사람이 테스트 코드만 보고 어떠한 테스트를 하는 것인지 한눈에 파악할 수 있도록 가독성있게 작성하는 것이 좋다.
    - 테스트의 설명을 구체적으로 작성하고, 하나의 테스트에서 너무 많은 테스트를 수행하지 않는 것이 좋다.
- **유지 보수가 가능한 테스트를 작성해야 한다.**
    - 애플리케이션 코드의 변경에 따라 테스트 코드도 관리되어야 한다. 필요 이상으로 너무 작은 단위의 테스트는 변경 사항에 취약하며 유지 보수를 어렵게 만든다.
    - 적절한 범위로 나누어 작성하자.

# Trade Off

테스트 코드를 작성하는 것은 큰 비용이 들어가며, 지속적으로 유지 보수해야 한다. 테스트로 모든 코드를 검증하려면 엄청난 비용이 들 것이며, 테스트의 실행 시간도 증가할 것이다.

100% 테스트 커버리지를 목표로 하는 것이 아니라 애플리케이션의 문맥 안에서 검증해야 하는 것이 무엇인지를 근본적으로 생각하자!

(예를 들어 영화 예매 기능을 검증한다면, 상영 영화 정보를 올바르게 가져오거나 인원수 또는 할인 조건에 따라 예매 요금 계산을 올바르게 하는지 등등)

# TDD (Test Driven Development)

> 개발과 시작의 끝이 테스트이며 자연스럽게 코드의 결과를 검증하며 개발을 진행하는 것이 테스트 주도 개발이다.
> 

**테스트 주도 개발 과정**

1. **적색** : 추가하려는 기능을 개발하기 전에 테스트를 먼저 작성한다. 이렇게 하면 당연히 테스트가 실패하게 된다.
2. **녹색** : 코드를 구현하여 테스트를 통과한다.
3. **리팩토링** : 작성한 코드를 살펴보고 이해하기 쉬우며 잘 설계되었는지 확인하여 리팩토링을 수행한다. 리팩토링 과정 속에서 문제가 발생하여도 이를 알려주는 테스트가 있기 때문에 문제의 원인을 금방 찾아 해결할 수 있다.
4. **반복** : 모든 구현이 완료될 때까지 과정을 반복한다.

👎 검증해야 하는 것이 무엇인지 고민하지 않고 맹목적으로 TDD를 적용한다면 Trade Off가 발생할 것. 이는 오히려 개발 생산성을 저하시키고 시간 낭비가 될 수 있다.

👍 테스트의 대상과 범위, 검증해야할 것이 무엇인지를 고민하고 적절한 단위로 나누어 테스트를 실행하자.

# 테스트의 종류

완벽하게 테스트하는 것은 불가능하기 때문에 어떠한 테스트가 적합한지 전략적으로 접근하는 것이 좋다. 모든 상태나 동작을 단위 테스트로 검증할지, 개별 단위 테스트보다 통합 테스트를 사용하여 여러 요소의 상호작용이 제대로 이루어지는지 검증할지 효율적인 방법에 대해 고민해야 한다.

크게 애플리케이션의 동작 및 워크 플로우를 검증하는 **단위 테스트, 통합 테스트, E2E 테스트**와 레이아웃이나 스타일링처럼 시각적인 요소들을 비교하여 검증하는 **시각적 회귀 테스트**가 있다.

### 단위 테스트

> 단위 테스트는 가장 기본적인 테스트로, 단일 함수의 결괏값 또는 클래스나 컴포넌트의 상태나 행위를 검증한다. 다른 요소와의 상호작용을 검증하기보다는 각 요소의 동작을 독립적으로 검증하는 테스트이다.
> 
- 각각의 요소가 올바르게 동작하는지 검증되여야 통합 테스트, E2E 테스트에서 이러한 단위 테스트들의 검증 결과를 믿고, 더 큰 범주의 테스트를 실행할 수 있다.
- 모든 행위나 상태를 다 검증하기보다는 외부에 인터페이스로 노출되는 코드 또는 중요한 연산을 처리하는 코드를 검증하는 것이 좋다. 내부 구현에 종속적인 검증이 아니기 때문에 좋은 테스트가 될 수 있다.

### 통합 테스트

> 일부 개별 요소들이 조합되었을 때 올바르게 동작하는지 확인한다. 어떠한 행위에 의해 모든 컴포넌트(요소)의 상태가 올바르게 변경되는지 테스트하는 것을 목표로 한다.
> 
- 여러 요소의 상호작용을 검증하는 테스트이기 때문에 단위 테스트에 비해 테스트의 사전 환경 설정이 복잡할 수 있으며, ‘모킹’이 필요할 수 있다.
    - 이때, 최대한 적게 모킹하는 것이 좋다. 모의 객체를 너무 많이 사용하면 올바른 시나리오로 검증되고 있는 것인지 파악하기 어려울 수도 있으며 테스트 자체의 신뢰도를 떨어뜨릴 수 있다.

### E2E 테스트

> End-To-End 테스트는 그대로 실제 애플리케이션을 실행하여 전체 워크 플로우를 검증하는 테스트이다. 진짜 사용자가 사용하는 것처럼 시나리오를 작성하여 검증하는 것이 핵심이다.
> 
- 애플리케이션 자체를 구동하여 테스트를 실행하기 때문에 설정 과정이나 테스트 실행 시간이 가장 오래 걸리는 테스트이다.
- 예를 들면 영화 예매 시스템에서 사용자가 로그인 하고 예매하려는 영화와 시간, 좌석 위치 등을 선택하고 할인 쿠폰을 적용하여 결제하는 흐름을 검증하는 것

# 사용자 관점의 테스트가 중요한이유

- 상태를 직접 조작할 경우, 가독성이 떨어지고 코드상에서 일일이 상태를 직접 변경해야 하거나 특정 모듈이나 객체의 프로퍼티 또는 메서드에 깊게 접근하여 상태를 변경해야 할 수도 있다.
- 메서드를 직접 호출하여 검증할 경우, 테스트 결과와 애플리케이션의 실제 구동 결과가 다를 수 있다.

<aside>
💡 테스트를 작성하는 것은 Trade Off이다. 각각의 테스트에 들어가는 비용이 다르기 때문에 얻을 수 있는 효과와 신뢰성을 따져 보고 어떤 것이 Trade Off를 최소화할 수 있는지 균형을 찾아야 한다.
