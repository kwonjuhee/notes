# What is "Rendering"?

렌더링이란 컴포넌트에게 현재의 props와 state의 조합을 기준으로 UI 섹션이 어떻게 보이길 원하는지 설하도록 요청하는 React의 프로세스를 말한다.

## Rendering Process Overview

React는 컴포넌트 트리의 root에서 시작해서 아래쪽으로 반복하면서 업데이트가 필요하다고 플래그가 지정된 모든 컴포넌트를 찾는다. 플래그가 지정된 각 컴포넌트에 대해 React는 함수 컴포넌트의 경우 `FunctionComponent(props)` 또는 클래스 컴포넌트의 경우 `classComponentInstance.render()`를 호출하고, 다음 단계를 위해 렌더링 출력을 저장한다.

컴포넌트의 렌더링 출력은 일반적으로 JSX 구문으로 작성되며 js가 컴파일되고 배포를 준비할 때 `React.createElement()` 호출로 변환된다. `createElement`는 UI의 구조를 설명하는 일반 js 객체인 [[React Element]]를 반환한다.

```jsx
// This JSX syntax:
return <MyComponent a={42} b="testing>text here</MyComponent>

// is converted to this call:
return React.createElement(MyComponent, {a: 42, b: "testing"}, "text here")

// and that becomes this element object:
{type: MyComponent, props: {a: 42, b: "testing"}, children: ["text here:]}

// And internally, React calls the actual function to render it:
let elements = MyComponent({...props, children})
```

```jsx
// For "host components" like HTML:
return <button onClick={() => {}}>Click Me</button>
// becomes
React.createElement("button", {onClick}, "Click Me")
// and finally:
{type: "button", props: {onClick}, children: ["Click me"]}
```

전체 컴포넌트 트리의 render output을 모은 후 React는 새로운 객체 트리(aka virtual DOM)를 비교하고 real DOM에 적용되어야 할 변경 사항 목록을 수집한다. 이러한 과정을 [[react/재조정 (Reconciliation)|재조정 (Reconciliation)]]이라 한다.

그런 다음 React는 계산된 모든 변경사항을 하나의 동기적 시퀀스로 실제 DOM에 적용한다.

> Note
> 
> React 팀은 virtual DOM이라는 용어를 지양한다. virtual DOM이라는 용어는 DOM이슈를 해결하기 위한 수단으로 들리기 때문이다. 하지만 이것은 React가 하는 것이 아니다.
> 
> React의 핵심 원칙은 UI는 value(문자열이나 배열처럼)라는 것이다. 변수에 보관하고, 전달하고, 자바스크립트 제어 흐름을 사용할 수 있다. 이러한 표현력(expressiveness)이 요점이다. DOM에 변경사항을 적용하는 것을 피하기 위한 diffing이 아니라!
> 
> 심지어 항상 DOM을 DOM을 나타내는 것도 아니다. 예를 들어, `<Message recipientId={10} />`은 DOM이 아니다. 개념적으로 lazy function call(`Message.bind(null, {recepientId: 10}`)을 나타낸다.

## Render and Commit Phases

React 팀은 렌더링 작업을 개념적으로 두 단계([[Render & Commit Phase]])로 나눈다.

- **Render Phase**는 컴포넌트를 렌더링하고 변경사항을 계산하는 모든 작업을 포함한다.
- **Commit Phase**는 변경사항을 DOM에 적용하는 과정이다.

React는 commit phase에서 DOM을 업데이트한 후 요청된 DOM 노드와 컴포넌트 인스턴스를 가리키도록 모든 참조를 업데이트한다. 그런 다음 동기적으로 componentDidMount 및 copmonentDidUpdate class lifecycle method와 useLayoutEffect hook을 동기적으로 실행한다.

그런 다음 짧은 timeout 후에 모든 `useEffect` hook을 실행한다. 이 단계는 "Passive Effects" 단계라고도 한다.

React 18은 [[동시성 렌더링 (Concurrent Rendering)]] 기능을 추가했다. React는 브라우저가 이벤트를 처리할 수 있도록 렌더링 단계에서 작업을 일시 중지 수 있는 기능을 제공한다. 렌더링 패스가 완료된 이후에도 React는 commit phase를 한 단계에서 동기적으로 실행한다.

여기서 이해해야 할 핵심 부분은 "렌더링"은 "DOM 업데이트"와 다르며 컴포넌트는 결과적으로 가시적인 변경사항이 발생하지 않고도 렌더링될 수 있다는 점이다. React가 컴포넌트를 렌더링할 때
- 컴포넌트는 지난번과 동일한 렌더링 출력을 반환할 수 있으므로 변경사항이 필요하지 않다.
- 동시성 렌더링에서 React는 컴포넌트를 여러번 렌더링할 수 있지만 다른 업데이트가 현재 수행중인 작업이 무효화(invalidate)되면 매번 렌더링 출력을 버린다.

# React는 렌더링을 어떻게 다룰까?

## Queuing Renders

초기 렌더링이 완료된 후 React에게 리렌더링을 queue하도록 하는 방법에는 여러가지가 있다.

- Function components
    - `useState` setters
    - `useReducer` dispatches
- Class components
    - `this.setState()`
    - `this.forceUpdate()`
- Other
    - Calling the ReactDOM top-level `render(<App>)` method again (which is equivalent to calling `forceUpdate()` on the root component)
    - Updates triggered from the new `useSyncExternalStore` hook

> 함수 컴포넌트에는 `forceUpdate` 메서드가 없지만 항상 카운터를 증가시키는 `useReducer` hook을 사용하면 동일한 동작을 얻을 수 있다.

### 표준 렌더링 동작

React의 기본 동작은 **부모 컴포넌트가 렌더링될 때 모든 자식 컴포넌트를 재귀적으로 렌더링**한다는 것이다.

예를 들어, 컴포넌트 트리가 `A > B > C > D`로 되어 있고 이미 페이지에 표시했다고 가정해 보자. 유저는 B에서 카운터를 증가시키는 버튼을 클릭한다.
- `B`에서 `setState()`를 호출하면 `B`의 리렌더링이 queue된다.
- React는 트리의 맨 위부터 렌더링 패스를 시작한다.
- React는 `A`가 업데이트가 필요하다고 표시되지 않은 것을 확인하고 이를 지나친다.
- React는 `B`를 업데이트가 필요하다고 표시된 것을 보고 그것을 렌더링한다. `B`는 지난번과 마찬가지로 `<C />`를 반환한다.
- `C`는 원래 업데이트가 필요하다고 표시되지 않았지만 부모 `B`가 렌더링되었기 때문에 React는 이제 아래로 이동하여 `C`도 렌더링한다. `C`는 다시 `<D />`를 반환한다.
- `D` 또한 렌더링이 필요한 것으로 표시되지 않았지만 부모 `C`가 렌더링되었기 문에 React는 아래로 이동하여 `D` 또한 렌더링한다.

즉, **컴포넌트를 렌더링하면 기본적으로 그 안에 있는 모든 컴포넌트도 역시 렌더링된다!**

또 다른 핵심 포인트는 **일반적인 렌더링에서 React는 props가 변경되었는지 신경쓰지 않고 부모 컴포넌트가 렌더링되었다는 이유만으로 무조건 자식 컴포넌트를 렌더링한다는 것**이다.

즉, root \<App> 컴포넌트에서 다른 변경 없이 `setState()`를 호출하는 것은 컴포넌트 트리의 모든 컴포넌트를 리렌더링하게 된다는 것을 의미한다. 결국 React의 원래 세일즈 피치 중 하나는 "업데이트할 때마다 전체 앱을 다시 그리는 것처럼 동작한다"는 것이었다.

이제 트리에 있는 대부분의 컴포넌트가 지난번과 동일한 렌더링 출력을 반환할 가능성이 매우 높기 때문에 React는 DOM을 변경할 필요가 없다. 하지만 React는 여전히 **컴포넌트에 렌더링을 요청하고 렌더링 출력을 diffing하는 작업을 수행**해야한다. 두 작업 모두 시간과 노력이 필요하다.

렌더링은 나쁜 것이 아니라 React가 실제로 DOM을 변경할 필요가 있는지 여부를 파악하는 방법이라는 것을 기억하자.

## 리액트 렌더링 규칙

리액트 렌더링의 주요 규칙 중 하나는 **렌더링은 "순수(pure)"해야 하고 어떤 side effects도 없어야 한다는 것**이다.

많은 side effects가 명확하지 않고 어떤 것도 망치지 않을 수 있기 때문에 까다롭고 혼란스러울 수 있다. Sebastian Markbage가 작성한 [The Rules of React](https://gist.github.com/sebmarkbage/75f0838967cd003cd7f9ab938eb1958f)에 따르면 React 라이프사이클 메서드에 대해 예상되는 동작과 어떤 종류의 연산이 "순수"한지 또 어떤 것이 안전하지 않은지를 정의한다.

- render logic **must not**
	- 존재하는 변수나 객체를 변경할 수 없다.
	- 랜덤 값을 생성할 수 없다. `Math.random()` 이나 `Date.now()` 같은
	- 네트워크 요청을 할 수 없다.
	- 상태 업데이트를 할 수 없다.
- render logic **may**
	- 렌더링 중 새로 생성되는 객체를 변경시킬 수 있다.
	- 에러를 던질 수 있다.
	- 아직 생성되지 않은 데이터(cached value같은)를 lazy initialize할 수 있다. 

## Component Metadata and Fibers

React는 어플리케이션에 존재하는 모든 컴포넌트 인스턴스를 추적하는 내부적인 자료구조를 저장한다. 이 자료구조는 "fiber"라고 불리는 객체다. 이 데이터 구조의 핵심은 [[Fiber#unit of work]]라는 객체로 다음을 설명하는 메타 데이터 필드를 포함한다.
- 컴포넌트 트리에서 이 시점에 렌더링되어야 하는 컴포넌트의 타입
- 이 컴포넌트와 연관된 현재 props와 state
- parent, sibling, child 컴포넌트에 대한 포인터
- React가 렌더링 프로세스를 추적하는 데에 사용되는 기타 내부적인 메타데이터
- https://github.com/facebook/react/blob/v18.0.0/packages/react-reconciler/src/ReactInternalTypes.js#L64-L193

렌더링 과정동안 React는 **fiber 객체 트리를 순환하고 새로운 렌더링 결과를 계산하면서 업데이트된 트리를 구축**할 것이다.

fiber 객체는 **실제 컴포넌트 props와 state 값을 저장**한다는 점을 주목하자. 컴포넌트에서 props와 state를 사용할 때 React는 실제로 fiber 객체에 저장된 값에 대한 접근 권한을 부여한다. 실제로 클래스 컴포넌트의 경우, React는 렌더링하기 전에 명시적으로 `componentInstance.props = newProps`를 컴포넌트에 복사한다. 따라서 `this.props`는 React가 내부 자료 구조로부터 참조를 복사했기 때문에 존재할 뿐이다. 그런 의미에서 컴포넌트는 React fiber 객체에 대한 일종의 외관(facade)이다.

마찬가지로 React hook은 **컴포넌트의 모든 hook을 해당 컴포넌트의 fiber 객체와 연결된 linked list로 저장**하기 때문에 작동한다. React는 함수 컴포넌트를 렌더링할 때 fiber에서 hook 설명 객체의 linked list를 가져오고, hook을 호출할 때마다 hook 설명 객체에 저장된 적절한 값(`useReducer`의 state와 dispatch value같은)을 반환한다.

부모 컴포넌트가 주어진 자식 컴포넌트를 **처음으로 렌더링할 때 React는 컴포넌트 "인스턴스"를 추적하는 fiber 객체를 생성**한다. 클래스 컴포넌트의 경우, 말 그대로 `const instance = new YourComponentType(props)`를 호출하고 실제 컴포넌트 인스턴스를 fiber 객체에 저장한다. 함수 컴포넌트의 경우, React는 `YourComponentType(props)`를 함수로 호출하기만 하면 된다.


## Component Type and Reconciliation

재조정 알고리즘 [[Diffing Algorithm]] 에서 설명하는 것처럼 React는 리렌더링시 기존 컴포넌트 트리와 DOM 구조를 가능한 많이 재사용하여 효율성을 높이려고 한다. **트리의 같은 위치에 있는 같은 type의 컴포넌트나 HTML 노드를 렌더링하도록 요청하면 React는 처음부터 다시 생성하는 대신 이를 재사용하고 필요한 경우에만 업데이트를 적용한다.** 즉, React는 동일한 위치에 같은 컴포넌트를 렌더링하도록 요청하는 한 컴포넌트 인스턴스를 계속 유지한다는 것을 의미한다. 클래스 컴포넌트의 경우 실제로 동일한 컴포넌트 인스턴스를 사용한다. 함수 컴포넌트에는 클래스처럼 진정한 인스턴스가 없지만, "이 유형의 컴포넌트가 여기에 표시되고 유지되고 있다"는 측면에서 `<MyFunctionComponent />`는 "instance"를 나타낸다고 생각할 수 있다.

그렇다면 React는 언제, 어떻게 출력이 실제로 변경되었는지 알 수 있을까?

React 렌더링 로직은 **`type` 필드를 기준**으로 요소를 비교한다. **`===` 참조 비교**를 사용한다. 만약 요소가 다른 type으로 변경되었다면(div -> span or \<ComponentA/> -> \<ComponentB/>) React는 **하위 트리 전체가 변경되었다고 가정**하고 비교 프로세스의 속도를 높일 것이다. 결과적으로 React는 **모든 DOM 노드를 포함하여 존재하는 모든 트리 영역을 파괴하고 새 컴포넌트 인스턴스로 다시 생성**할 것이다.

이는 렌더링이 일어나는 동안 새로운 컴포넌트 타입을 생성해서는 안된다는 것을 의미한다. 새로운 컴포넌트 타입을 생성할 때마다 다른 참조를 갖게되며 이 React가 반복적으로 자식 컴포넌트 트리를 파괴하고 재생성하게 한다.

```jsx
// ❌ BAD!
// This creates a new `ChildComponent` reference every time!
function ParentComponent() {
  function ChildComponent() {
    return <div>Hi</div>;
  }

  return <ChildComponent />;
}
```

```jsx
// ✅ GOOD
// This only creates one component type reference
function ChildComponent() {
  return <div>Hi</div>;
}

function ParentComponent() {
  return <ChildComponent />;
}
```


## Key and Reconciliation

React가 컴포넌트 인스턴스를 식별하는 다른 방법은 **`key` prop**을 사용하는 것이다. React는 **컴포넌트 타입의 특정 인스턴스를 구별**하기 위해 key를 고유한 식별자로 사용한다.

key는 실제 prop이 아니라 React에 대한 명령어라는 점에 유의하자. React는 항상 이를 제거하며 절대 실제 컴포넌트로 전달되지 않으므로 `props.key`를 가질 수 없다.

리스트를 렌더링할 때 key를 주로 사용한다. 리스트 항목을 재정렬, 추가 또는 삭제 등 어떤 식으로든 변경될 수 있는 데이터를 렌더링하는 경우 key가 특히 중요하다. key는 가능하면 고유한 id를 사용해야 하며 배열 인덱스는 최후의 수단으로만 사용해야 한다.

```jsx
// ✅ Use a data object ID as the key for list items
todos.map((todo) => <TodoListItem key={todo.id} todo={todo} />);
```

만약 배열 인덱스를 key로 사용하여 10개의 `<TodoListItem />` 컴포넌트 목록을 렌더링한다고 가정해보자. React는 0~9의 key를 가진 10개의 아이템을 인식한다. 이제 아이템 6과 7을 삭제하고 마지막 3개의 새 항목을 추가하면 0~10의 key를 가진 아이템들을 렌더링하게 된다. 리스트가 10개에서 11개로 바뀌었기 때문에 React에서는 실제로 마지막에 새 항목 하나를 추가한 것처럼 보인다. React는 기존 DOM 노드와 컴포넌트 인스턴스를 기꺼이 재사용할 것이다. 하지만 이는 `<TodoListItem key={6} />`을 아이템 8로 렌더링할 것이라는 의미이다. 따라서 컴포넌트 인스턴스는 여전히 유지되지만 이전과는 다른 데이터 객체를 prop으로 가져오게 될 것이다. 이것은 동작할 수 있지만 예기치 않은 동작이 발생할 수 있다.
또한 React는 기존 리스트 아이템이 이전과 다른 데이터를 보여주어야 하므로 몇몇의 아이템에 업데이트를 적용해야 할 것이다. 리스트 아이템이 변경되지 않았기 때문 이 업데이트들은 실제로 필요하지 않다.

대신 각 리스트 아이템에 `todo.id`를 key로 사용했다면 React는 삭제된 두 아이템과 추가된 세 아이템을 올바르게 인식한다. 삭제된 두 개의 컴포넌트 인스턴스와 관련된 DOM은 제거하고 추가된 세 개의 컴포넌트 인스턴스와 DOM을 생성할 것이다. 이는 실제로 변경되지 않은 컴포넌트를 불필요하게 업데이트하는 것보다 낫다.

key는 리스트 외에도 컴포넌트 인스턴스를 식별하는 데에도 유용하다. 언제든지 React 컴포넌트에 key를 추가하여 식별자를 나타낼 수 있고 해당 key를 변경하면 React가 이전 컴포넌트 인스턴스를 제거하고 새 인스턴스를 생성할 것이다. 일반적은 사용 사례는 리스트 + 상세정보 form의 조합이다. 이때 form은 선택된 목록 항목의 데이터를 표시한다. `<DetailForm key={selectedItem.id} />`를 렌더링하면 선택한 항목이 변경될 때 React가 for을 제거하고 다시 생성하므로 form 내부의 stale state 문제를 피할 수 있다.

## Render Batching and Timing

기본적으로 setState() 호출은 React가 새로운 렌더링 패스를 생성하게 하고 그것을 동기적으로 실행한 후 반환한다. 하지만 React는 또한 **렌더링 일괄 처리(batching)의 형태로 일종의 최적화를 자동으로 적용**한다. 렌더링 배칭은 **setState를 여러번 호출할 때 약간의 지연으로 하나의 렌더링 패스가 queue되고 실행되는 것**을 말한다.

React 커뮤니티에서는 이를 "상태 업데이트가 비동기적일 수 있다"라고 설명하기도 한다. 새로운 React docs에서는 [[State as a Snapshot]]이라고 설명하기도 한다. https://react.dev/learn/state-as-a-snapshot

React 17과 그 이전에 React는 오직 리액트 이벤트 핸들러에서만 배칭을 수행했다. 이벤트 핸들러 외부에서 queue된 업데이트(setTimeout, await 후, js 이벤트 핸들러)는 queue되지 않았고 별도의 리렌더링이 발생했다.

하지만 React 18은 단일 이벤트 루프 tick에서 대기중인 모든 업데이트들의  [[automatic batching]]을 수행한다. 이는 필요한 전체 렌더링 횟수를 줄일 수 있다.

```jsx
const onClick = async () => {
  setCounter(0);
  setCounter(1);

  const data = await fetchSomeData();

  setCounter(2);
  setCounter(3);
}
```

- react 17에서는 3번의 리렌더링이 수행되었다.
	- 첫번째 패스는 `setCounter(0)`과 `setCounter(1)`를 일괄 처리할 것이다. 왜냐하면 둘다 이벤트 핸들러 call stack동안 발생하므로 둘다 `unstable_batchedUpdates()` 호출 내부에서 발생한다.
	- 하지만 await으로 인해 `setCounter(2)`에 대한 호출은 `await` 후에 발생한다. 
	- `await`으로 인해 동기적인 call stack이 완료되고 함수의 남은 반쪽이 완전히 분리된 콜 스택에서 나중에 수행된다. 이것 때문에 React는 `setCounter(2)` 호출 내부에서 마지막 단계로 전체 렌더링 패스를 동기적으로 수행한다.
	- `setCounter(3)`에서도 마찬가지이다. 원래의 이벤트 핸들러 밖에서, 배칭 외부에서 실행되기 때문이다.
- react 18에서는 2번의 리렌더링을 수행한다.
	- 한 이벤트 루프 tick에 있는 0과 1 / 2와 3을 배치 처리한다.


## Async Rendering, closures, and state snapshots

엄밀히 말하면 **리액트 렌더링은 동기적**이다. 이것은 이벤트 루프 tick 끝에 있는 **microtask에서 수행**된다.

```jsx
function MyComponent() {
  const [counter, setCounter] = useState(0);

  const handleClick = () => {
    setCounter(counter + 1);

    console.log(counter); // original value was logged - why is this not updated yet?
  };
}
```

위에서 언급했듯이 "React 상태 업데이트는 비동기적"이라고 말하는 것이 일반적이다. 하지만 엄밀히 말하면 React 렌더링은 말 그대로 동기식이며 이벤트 루프 tick 끝에 있는 마이크로태스크에서 수행된다. handleClick의 관점에서 봤을 때 결과를 즉시 확인할 수 없으므로 **실제 업데이트는 `setCounter` 호출보다 훨씬 늦게 발생한다는 점에서 비동기(async)이다.**

이것이 작동하지 않는 더 큰 이유가 있다. **handleClick 함수는 클로저이며 함수가 정의되었을 때 존재했던 변수 값만 볼 수 있기 때문**이다. 다시 말해 이러한 state 변수는 시간의 snapshot이다.

`handleClick`은 이 함수 컴포넌트의 가장 최근 렌더링 중에 정의되었으므로 해당 렌더링 패스중에 존재했던 `counter` 값만 볼 수 있다. `setCounter`를 호출했을 때 미래의 렌더링 패스를 queue하고 해당 렌더링에는 새로운 값을 가진 새로운 `counter` 변수와 새로운 `handleClick` 함수가 있지만 `handleClick` 복사본은 절대 새로운 값을 볼 수 없을 것이다.


## Render Behavior Edge Cases

### Commit Phase Lifecycles

commit phase 라이프사이클 메서드 안에는 `componentDidMount`, `componentDidUpdate`, `useLayoutEffect`와 같은 추가 엣지 케이스들이 있다. 이러한 메서드는 주로 렌더링 후 브라우저가 페인팅하기 전에 추가 로직을 수행할 수 있도록 하기 위해 존재한다. 특히 일반적인 유즈 케이스는 다음과 같다.

- 부분적이지만 불완전한 데이터로 컴포넌트를 처음 렌더링한다.
- commit phase 라이프사이클에서 실제 DOM 노드의 크기를 실측하기 위해서 ref를 사용한다.
- 해당 측정값을 기반으로 컴포넌트의 일부 state를 설정한다.
- 업데이트된 데이터로 즉시 리렌더링한다.

이 유즈 케이스에서는 부분적으로 렌더링된 UI가 보여지는 것이 아니라 최종 UI만 보여지기를 원한다. 브라우저는 DOM 구조가 수정되면 다시 계산하지만 js 스크립트가 여전히 실행 중이고 이벤트 루프를 차단하는 동안에는 실제로 화면에 아무것도 그리지 않을 것이다. 따라서 `div.innerHTML = "a";` `div.innerHTML = "b"` 와 같이 DOM 수정을 여러 번 실행할 수 있으며 "a"는 절대 나타나지 않는다.

이 때문에 React는 항상 commit phase의 라이프사이클을 **동기적으로 실행**한다. 이렇게 하면 최종 콘텐츠만 화면에 표시될 수 있다.

useEffect 콜백의 상태 업데이트는 queue되었다가 모든 useEffect 콜백이 완료되면 "Passive Effects" 단계가 끝날 때 flush된다.

### Reconciler Batching Methods

React reconciler는 렌더링 배칭을 변경하는 메서드가 있다.

- React 17 이하에서는 이벤트 핸들러 외부의 여러 업데이트를 `unstable_batchedUpdates()`로 감싸 배치 처리할 수 있다.
- React 18부터는 기본적으로 자동으로 일괄 처리되기 때문에 automatic batching을 중단하고 즉각적인 렌더링을 강제하는 `flushSync()` API가 있다.

### \<StrictMode>

React는 개발시 \<StrictMode> 태그 안에 있는 컴포넌트를 더블 렌더링한다. 즉 렌더링 로직이 실행되는 횟수는 커밋된 렌더링 패스의 횟수와 같지 않으며, 발생한 렌더링 횟수를 계산하기 위해 `console.log()`문에 의존할 수 없다. 대신 React DevTools Profiler를 사용하여 커밋된 렌더링 횟수를 세거나 `useEffect` hook이나 `componentDidMount/Update` 라이프사이클에 로깅을 추가할 수 있다. 이렇게 하면 React가 실제로 렌더링 패스를 완료하고 커밋했을 때만 로그가 남는다.

### Setting State While Rendering

일반적인 상황에서는 실제 렌더링 로직에 있는 동안 상태 업데이트를 queue하면 안된다. 즉 click이 발생했을 때 setSomeState()를 호출하는 click 콜백을 생성하는 것은 괜찮지만 실제 렌더링 동작의 일부로 setSomeState()를 호출해서는 안된다.

하지만 한 가지 예외가 있다. 함수 컴포넌트는 조건부로 수행되고 이 컴포넌트가 렌더링될 때마다 실행되지 않는 한 렌더링하는 동안 setSomeState()를 직접 호출할 수 있다. 이 함수는 클래스 컴포넌트에서 `getDerivedStateFromProps`(https://reactjs.org/docs/hooks-faq.html#how-do-i-implement-getderivedstatefromprops)에 해당하는 함수 컴포넌트 역할을 한다. 만약 함수 컴포넌트가 렌더링하는 동안 상태 업데이트를 queue하면 React는 즉시 상태 업데이트를 적용하고 동기적으로 리렌더링한 후 다음 단계로 넘어간다.
만약 컴포넌트가 상태 업데이트를 queue하고 React가 리렌더링하도록 강제하는 것을 무한정 계속 하게 되면 React는 설정된 재시도 횟수(현재 50회)를 넘으면 루프를 중단하고 오류를 발생시킨다. 이 기법은 prop 변경에 따라 즉시 상태 값 업데이트를 강제할 수 있으며, 리렌더링이 필요하지 않고 useEffect 내부에서 setSomeState()를 호출할 필요도 없다.



# 렌더링 성능 향상시키기

컴포넌트의 렌더링 출력이 변경되지 않았고 DOM의 해당 부분을 업데이트할 필요가 없다면 렌더링 작업이 시간 낭비가 될 수도 있다.

React 컴포넌트 렌더링은 항상 현재 props와 state를 기반으로 해야하기 때문에 props와 state가 변경되지 않았다는 것을 미리 알고 있다면 이 컴포넌트에 변경이 필요하지 않으며 렌더링 작업을 안전하게 건너뛸 수 있다는 것을 알아야 한다.

일반적으로 소프트웨어 성능을 개선하려고 할 때 두가지 기본 접근 방식이 있다.
- 동일한 작업을 더 빠르게 수행한다.
- 작업을 줄인다.
React 렌더링을 최적화하는 것은 주로 컴포넌트 렌더링을 적절하게 건너뛰어서 작업을 줄이는 것이다.

## 컴포넌트 렌더링 최적화 기법

React는 컴포넌트 렌더링을 생략할 수 있는 세 가지 기본 API를 제공한다.

- **`React.memo()`** : 컴포넌트 타입을 인자로 받아 새로운 wrapper 컴포넌트를 반환한다. 래퍼 컴포넌트의 기본 동작은 props가 변경되었는지 확인하고 변경되지 않은 경우 리렌더링을 막는 것이다. 함수 컴포넌트와 클래스 컴포넌트 모두에 사용 가능하다.
	- 사용자 정의 비교 콜백을 전달할 수 있다. 주로 모든 props 대신 특정 props 필드만 비교할 때 사용한다.
- **`React.Component.shouldComponentUpdate`** : 렌더링 프로세스 초기에 호출되는 클래스 라이프사이클 메서드이다. false를 반환하면 컴포넌트 렌더링을 건너뛴다. boolean 결과를 계산하는 로직을 포함할 수 있지만, 가장 일반적인 접근은 컴포넌트의 props와 state가 변경되지 않은 경우 false를 반환하는 것이다.
- **`React.PureComponent`** : props와 state를 비교하는 동작을 기본으로 한다. Component + `shouldComponentUpdate` 대신 사용할 수 있다.

이러한 접근은 모두 **"얕은 비교(shallow equality)"** 기법을 사용한다. 즉, 서로 다른 두 객체의 모든 개별 필드를 확인하고 객체의 내용 중 다른 값이 있는지 확인한다. (`obj1.a === obj2.a && obj1.b === obj2.b && ...`) js 엔진에서 `===` 비교는 매우 간단한 연산이기 때문에 일반적으로 빠른 프로세스이다. 따라서 이 세 가지 접근 방식은 `const shouldRender = !shallowEqual(newProps, prevProps)`와 동일한 작업을 수행한다.

잘 알려지지 않은 기법도 있다.
- output에 **`props.children`** 을 포함하면 컴포넌트가 상태 업데이트를 수행해도 해당 요소는 동일하다.
- **일부 요소를 `useMemo()`로 감싸면** 의존성이 변경될 때까지 동일하게 유지된다.
	- `React.memo`는 자식에 의해 제어되지만 이 방식은 부모 컴포넌트에 의해 제어된다.
```jsx
// The `props.children` content won't re-render if we update state
function SomeProvider({ children }) {
  const [counter, setCounter] = useState(0);

  return (
    <div>
      <button onClick={() => setCounter(counter + 1)}>Count: {counter}</button>
      <OtherChildComponent />
      {children}
    </div>
  );
}

function OptimizedParent() {
  const [counter1, setCounter1] = useState(0);
  const [counter2, setCounter2] = useState(0);

  const memoizedElement = useMemo(() => {
    // This element stays the same reference if counter 2 is updated,
    // so it won't re-render unless counter 1 changes
    return <ExpensiveChildComponent />;
  }, [counter1]);

  return (
    <div>
      <button onClick={() => setCounter1(counter1 + 1)}>
        Counter 1: {counter1}
      </button>
      <button onClick={() => setCounter1(counter2 + 1)}>
        Counter 2: {counter2}
      </button>
      {memoizedElement}
    </div>
  );
}
```

이 모든 기법에서 **컴포넌트 렌더링을 건너뛴다는 것은 React가 전체 하위 트리 렌더링도 건너뛴다는 것을 의미**하는데 이는 "재귀적으로 자식을 렌더링"하는 기본 동작을 중지하기 위한 신호를 효과적으로 설정하는 것이기 때문이다.

## 새 props 참조가 렌더링 최적화 미치는 영향

이미 **기본적으로 React는 props가 변경되지 않았더라도 중첩된 모든 컴포넌트를 리렌더링**한다는 것을 보았따. 즉, 자식 컴포넌트에 새로운 props를 전달하는 것이 문제가 되지 않는다. 동일한 props를 전달하든 말든 렌더링되기 때문이다. 따라서 다음과 같은 방식은 완전히 괜찮다.

```jsx
function ParentComponent() {
  const onClick = () => {
    console.log('Button clicked');
  };

  const data = { a: 1, b: 2 };

  return <NormalChildComponent onClick={onClick} data={data} />;
}
```

`ParentComponent`가 렌더링될 때마다 새 `onClick` 함수 참조와 새 `data` 객체를 생성할 것이고 `NormalChildComponent`의 props로 전달할 것이다.

이는 또한 **host component를 `React.memo`로 감싸서 렌더링을 최적화하려고 할 필요가 없다는 것을 의미**한다. 이러한 기본 컴포넌트 아래에는 자식이 없으므로 렌더링 프로세스는 어짜피 거기서 멈출 것이기 때문이다.

**하지만 자식 컴포넌트가 props가 변경되었는지 확인하여 렌더링을 최적화하려고 한다면 새 참조를 props로 전달하는 것은 자식 컴포넌트의 리렌더링을 유발할 것**이다. 만약 새 props 참조가 실제로 세로운 데이터라면 괜찮다. 하지만 부모 컴포넌트가 단지 callback 함수를 전달하는 것이라면 어떨까?

```jsx
const MemoizedChildComponent = React.memo(ChildComponent);

function ParentComponent() {
  const onClick = () => {
    console.log('Button clicked');
  };

  const data = { a: 1, b: 2 };

  return <MemoizedChildComponent onClick={onClick} data={data} />;
}
```

이제 `ParentComponent`가 렌더링할 때마다 `MemoizedChildComponent`는 props 값이 새로운 참조로 변경되었음을 인식하고 리렌더링하게 된다. 심지어 `onClick` 함수와 `data` 객체가 기본적으로 매번 동일해야 함에도 불구하고!

즉 다음을 의미한다.
- 대부분의 경우 렌더링을 건너뛰고 싶어도 `MemoizedChildComponent`는 항상 리렌더링할 것이다.
- old props와 new props를 비교하는 작업을 수행하는 것은 낭비이다.

마찬가지로  `<MemoizedChildComponent><OtherComponent /></MemoizedChildComponent>`를 렌더링하는 것 역시 자식 컴포넌트가 항상 렌더링된다. `props.children`이 항상 새로운 참조이기 때문이다.

## props 참조 최적화

클래스 컴포넌트는 항상 동일한 참조인 인스턴스 메서드를 가질 수 있으므로 실수로 새로운 callback 함수 참조를 생성하는 것을 걱정할 필요가 없다. 하지만 각각의 자식들에게 고유한 callback을 생성하거나 익명 함수에서 값을 캡처하여 자식에 전달해야 할 수도 있다. 이렇게 하면 **새로운 참조가 발생하고 렌더링하는 동안 자식 props로 새로운 객체를 생성할 것**이다. React에는 이러한 경우를 최적화하기 위한 빌트인 기능이 없다.

함수 컴포넌트의 경우 React는 **동일한 참조를 재사용하는데 도움이 되는 두 가지 hook을 제공**한다.
- 객체 생성이나 복잡한 계산과 같은 종류의 일반 데이터를 위한 **`useMemo`**
- callback 함수를 생성을 위한 **`useCallback`**

## 모든 것을 memoize 해야할까?

위에서 언급했듯이 props로 전달하는 모든 함수나 객체에서 `useMemo`와 `useCallback`을 사용할 필요는 없다. **자식에게 동작에 변화를 일으키는 경우에만 사용**하면 된다. (즉, `useEffect`의 의존성 배열 비교는 일관된 props 참조를 받기를 원하는 자식 요소에서 또 다른 유즈 케이스를 추가하므로 더 복잡해진다.)

항상 제기되는 질문은 "왜 React는 기본적으로 모든 것을 `React.memo()`로 래핑하지 않는가?"이다.

Dan Abramov는 **memoization도 여전히 props를 비교하는 비용이 발생**하며 **컴포넌트가 항상 새 props를 받기 때문에 memoization check가 리렌더링을 막을 수 없는 경우가 많다는 점**을 반복적으로 지적했다.

또한 모든 컴포넌트에 기본적으로 적용하려고 하면 **데이터를 불변성을 지키지 않고 변경하는 경우 버그가 발생할 수 있다.**

## 불변성과 렌더링

**React에서 상태 업데이트는 항상 불변적으로 수행되어야 한다.** 그 이유는 크게 두 가지이다.
- 무엇을 어디에서 mutate하느냐에 따라 컴포넌트가 렌더링될 것으로 예상한 시점에 렌더링되지 않을 수 있다.
- 데이터가 실제로 언제, 왜 업데이트되었는지에 대해 혼란을 야기한다.

몇 가지 구체적인 예를 살펴보자.

`React.memo` / `PureComponent` / `shouldComponentUpdate` 모두 **[[얕은 비교]]** 검사에 의존한다. 따라서 `props.someValue !== prevProps.someValue`를 수행하여 props가 새로운 값인지 알 수 있을 것이다.

만약 **`someValue`를 mutate 하면 `someValue`는 동일한 참조가 되고 해당 컴포넌트는 아무 것도 변경되지 않은 것으로 간주**한다.

특히 불필요한 리렌더링을 피하여 성능 최적화를 하려는 경우에 발생한다. props가 변경되지 않는 경우에 렌더링은 불필요하거나 낭비이다. mutate하면 컴포넌트는 아무것도 변경되지 않았다고 잘못 생각할 수 있으며 컴포넌트가 왜 리렌더링되지 않는지 혼란스러울 수 있다.

또 다른 문제는 `setState`와 `useReducer` hook이다. `setCounter()` 또는 `dispatch()`를 호출할 때마다 React는 리렌더링을 queue한다. 하지만 React는 **모든 hook 상태 업데이트가 객체/배열 참조이든 primitive 값이든 상관없이 새 상태 값으로 새 참조를 전달/반환 해야한다.**

React는 render phase에서 모든 상태 업데이트를 적용한다. React가 hook으로부터 상태 업데이트를 적용하려고 할 때 새 값이 동일한 참조인지 확인한다. React는 항상 업데이트를 queue한 컴포넌트의 렌더링을 완료하지만, 값이 이전과 동일한 참조이고 렌더링을 계속할 이유가 없으면 (부모가 렌더링된 경우와 같이) React는 컴포넌트에 대한 렌더링 결과를 버리고 렌더링 패스를 완전히 빠져나온다. 따라서 다음과 같이 배열을 mutate하면 컴포넌트가 리렌더링을 실패할 것이다.
```js
const [todos, setTodos] = useState(someTodosArray);

const onClick = () => {
  todos[3].completed = true;
  setTodos(todos);
};
```

기술적으로는 가장 바깥쪽 참조만 불변으로 업데이트하면 된다. 위 예제를 다음과 같이 변경하면 새로운 배열 참조를 생성하고 전달하게 되어 컴포넌트가 리렌더링될 것이다.

```js
const onClick = () => {
  const newTodos = todos.slice();
  newTodos[3].completed = true;
  setTodos(newTodos);
};
```

클래스 컴포넌트의 `this.setState()`와 함수 컴포넌트의 `useState`와 `useReducer` hook 간에 mutation 및 리렌더링과 관련하여 뚜렷한 차이가 있다는 점에 유의하자. **`this.setState()`는 mutation 여부에 전혀 상관하지 않고 리렌더링을 완료**한다. 따라서 이것은 리렌더링된다.

```js
const { todos } = this.state;
todos[3].completed = true;
this.setState({ todos });
```

모든 실제 렌더링 동작 외에도, mutation은 표준 React 단방향 데이터 흐름에 혼란을 야기한다. mutation을 사용하면 전혀 변경되지 않을 것으로 예상했던 값이 다른 코드에서 다른 값으로 보여지게 할 수 있다. 이렇게 되면 특정 상태가 실제로 언제, 왜, 어디서 변경되었는지 알기가 어려워진다.

결론은 React와 React 생태계가 불변 업데이트를 가정한다는 것이다. mutation은 버그가 발생할 위험이 있으니 하면 안된다.

> 🔎 **mutation**은 **변경 가능한(mutable) 값을 변경하는 것**을 말한다. 객체 state는 기술적으로 변이(mutation)할 수 있지만 React가 변경을 감지할 수 없으므로 상태 업데이트시 불변성(immutability)를 지켜 수행되어야 한다.

React DevTools Profiler를 사용해 어떤 컴포넌트가 렌더링되는지 확인할 수 있다.

또한, 개발 모드에서는 React가 훨씬 느리게 실행된다는 점을 기억해야 한다. 절대적인 렌더링 시간을 측정하려면 프로덕션 빌드를 사용하자.

# Context와 렌더링 동작

React의 Context API는 사용자가 제공한 단일 값을 컴포넌트 하위 트리에서 사용가능하도록 하는 메커니즘으로, 주어진 `<MyContext.Provider>` 안에 있는 모든 컴포넌트는 context 인스턴스로부터 해당 값을 읽을 수 있다.

context는 "상태 관리(state management)" 도구가 아니다. context에 전달되는 값은 직접 관리해야 한다. 이는 일반적으로 데이터를 React 컴포넌트 state에 유지하고 해당 데이터를 기반으로 context 값을 구성하는 방식으로 수행된다.

## Context 값 업데이트

React는 주변 컴포넌트가 provider를 렌더링할 때 context provider에 새로운 값이 주어졌는지 확인한다. 만약 provider의 값이 새로운 참조라면, React는 값이 변경되었고 해당 context를 소비(consume)하는 컴포넌트를 업데이트해야 한다는 것을 알 수 있다.

context provider에 새 객체를 전달하면 업데이트된다는 점에 유의하자.

```jsx
function GrandchildComponent() {
  const value = useContext(MyContext);
  return <div>{value.a}</div>;
}

function ChildComponent() {
  return <GrandchildComponent />;
}

function ParentComponent() {
  const [a, setA] = useState(0);
  const [b, setB] = useState('text');

  const contextValue = { a, b };

  return (
    <MyContext.Provider value={contextValue}>
      <ChildComponent />
    </MyContext.Provider>
  );
}
```

이 예시에서 `ParentComponent`가 렌더링될 때마다 context provider에 새로운 값이 주어지므로 `MyContext`를 소비하는 모든 중첩 컴포넌트가 리렌더링된다.

React의 관점에서 각 context provider는 객체, 배열, primitive 등 어떤 것이든 상관없이 단 하나의 값만 가질 수 있다. 현재 context를 소비하는 컴포넌트가 새 값의 일부만 신경쓰더라도 새 context로 인한 업데이트를 건너뛸 수 있는 방법은 없다.

컴포넌트에 `value.a`만 필요한데 업데이트가 수행되어 새로운 `value.b` 참조가 발생하는 경우 불변 업데이트 및 context 렌더링 규칙에 따라 해당 값도 새로운 참조가 되어야 하며 `value.a`를 읽는 컴포넌트도 렌더링된다.

## 상태 업데이트, Context, 그리고 리렌더

종합해보면

- `setState()`를 호출하면 해당 컴포넌트의 렌더링이 queue된다.
- React는 기본적으로 중첩된 컴포넌트를 재귀적으로 렌더링한다.
- context provider는 렌더링하는 컴포넌트에 의해 값이 주어진다.
- 그 값은 일반적으로 부모 컴포넌트의 상태로부터 온다.

이는 **기본적으로 context provider를 렌더링하는 부모 컴포넌트의 상태 업데이트는 context 값을 읽었는지 여부에 관계없이 모든 자손 컴포넌트를 렌더링하게 된다는 것을 의미**한다.

위의 예제를 다시 살펴보면 `GrandChildComponent`는 context 업데이트 때문이 아니라 `ChildComponent`의 리렌더링으로 인해 리렌더링되는 것을 볼 수 있다. React는 기본적으로 부모 컴포넌트가 렌더링될 때마다 자식과 손자 컴포넌트를 렌더링한다. 부모 컴포넌트가 `MyContext.Provider`에 새로운 context 값을 넣으면, `GrandChildComponent`는 렌더링할 때 새로운 값을 보고 이를 사용하지만 context 업데이트로 인해 `GrandChildCompoent`가 렌더링되는 것이 아니라 어짜피 일어날 일이었던 것이다.

## Context 업데이트와 렌더링 최적화

실제로 최적화를 시도하도록 예제를 수정하되, 하단에 `GreatGrandchildComponent`를 추가해 보겠다.

```jsx
function GreatGrandchildComponent() {
  return <div>Hi</div>
}

function GrandchildComponent() {
    const value = useContext(MyContext);
    return (
      <div>
        {value.a}
        <GreatGrandchildComponent />
      </div>
}

function ChildComponent() {
    return <GrandchildComponent />
}

const MemoizedChildComponent = React.memo(ChildComponent);

function ParentComponent() {
    const [a, setA] = useState(0);
    const [b, setB] = useState("text");

    const contextValue = {a, b};

    return (
      <MyContext.Provider value={contextValue}>
        <MemoizedChildComponent />
      </MyContext.Provider>
    )
}
```

`setA(42)`를 수행하면

- `ParentComponent`가 렌더링된다.
- 새로운 `contextValue` 참조가 생성된다.
- React는 `MyContext.Provider`가 새로운 context value를 갖고 있고 따라서 `MyContext`의 모든 소비자 컴포넌트를 업데이트해야 한다는 것을 인식한다.
- React는 `MemoizedChildComponent`를 리렌더링하려고 하지만 `React.memo`로 래핑되어있고 전달되는 props가 없으므로 `ChildComponent`의 렌더링을 완전히 건너뛴다.
- 하지만 `MyContext.Provider`의 업데이트가 있으므로 React는 계속 아래로 내려가서 이를 알아야 하는 컴포넌트를 찾는다.
- `GrandchildComponent`에 도달하면 `MyContext`를 읽었으므로 해당 컴포넌트를 리렌더링한다.
- `GrandchildComponent`가 렌더링되었기 때문에 React는 계속 진행하며 그 안에 있는 것도 렌더링한다. 따라서 `GreatGrandchildComponent`도 리렌더링한다.

즉, Sophie Alpert에 따르면 **1) context provider 바로 아래에 있는 컴포넌트는 `React.memo`를 사용해야 한다**고 한다. 이렇게 하면 부모 컴포넌트의 상태 업데이트가 모든 컴포넌트를 강제로 리렌더링하지 않고 context만 읽히는 섹션만 렌더링할 것이다.

> **2) 한 레벨 위에서 "동일 요소 참조" 기법을 활용하여 자식 컴포넌트가 리렌더링되지 않도록** 하여 동일한 결과를 얻을 수도 있다. (`<MyContext.Provider>{props.children}</ MyContext.Provider>`)

하지만 `GrandchildComponent`가 다음 context 값을 기반으로 렌더링되면 React는 모든 것을 재귀적으로 리렌더링하는 기본 동작으로 바로 돌아간다. 따라서 `GreatGrandchildComponent`가 렌더링되었고 그 아래의 다른 모든 것도 렌더링되었을 것이다.

## Context와 Renderer Boundaries

일반적으로 React 앱은 ReactDOM이나 React Native와 같은 단일 렌더러로만 빌드된다. 하지만 핵심 렌더링 및 reconciling 로직은 react-reconciler라는 패키지로 게시되며 이를 사용하여 다른 환경을 대상으로 하는 자신만의 React 버전을 빌드할 수 있다. (예: Three.js 모델과 WebGL 렌더링을 구동하는 react-three-fiber, React를 사용해 터미널 텍스트 UI를 그리는 ink)

한 가지 오랜 한계는 앱에 여러 렌더러가 있는 경우 context provider가 렌더러 경계를 통과하지 못한다는 점이다.

```jsx
function App() {
  return (
    <MyContext.Provider>
      <DomComponent>
        <ReactThreeFiberParent>
          <ReactThreeFiberChild />
        </ReactThreeFiberParent>
      </DomComponent>
    </MyContext.Provider>
  );
}
```

위의 예제에서 `ReactThreeFiberParent`가 React-Three-Fiber로 렌더링되는 콘텐츠를 생성하고 표시하는 경우 `<ReactThreeFiberChild />`가 `<MyContext.Provider>`의 값을 볼 수 없게 된다.

이는 React의 알려진 한계이며 현재 이 문제를 해결할 수 있는 공식적인 방법은 없다.

React-Three-Fiber를 개발한 조직은 context bridging을 가능하게 하는 몇가지 내부 hack을 가지고 있으며 유효한 해결방법인 `useContextBridge` hook이 포함된 라이브러리를 릴리즈했다.

# React-Redux과 렌더링 동작

사람들은 Redux를 context와 비교했을 때 실제로 렌더링해야 하는 컴포넌트만 다시 렌더링하므로 context보다 더 낫다고 말한다.

이는 어느 정도 사실이지만 훨씬 더 미묘한 차이가 있다.

## React-Redux 구독

React-Redux는 context를 사용하여 현재 상태 값이 아닌 Redux store 인스턴스를 전달한다. 즉, 항상 동일한 context 값을 `<ReactReduxContext.Provider>`에 전달한다는 뜻이다.

Redux store는 action이 dispatch될 때마다 subscriber notification callback을 실행한다는 것을 기억해라. Redux를 사용해야 하는 UI 레이어는 항상 Redux store에 구독하고, subscriber callback에서 최신 상태를 읽고, 값을 비교하고, 관련 데이터가 변경된 경우 리렌더링한다. subscription callback 프로세스는 완전히 React 외부에서 일어나며 React-Redux가 특정 React 컴포넌트에 필요한 데이터가 변경되었다는 것을 알고 있는 경우에만 React가 관여한다. (`mapState`의 반환 값 또는 `useSelector`에 따라)

그 결과 context는 매우 다른 성능 특성이 나타난다. 항상 렌더링하는 컴포넌트의 수는 줄어들겠지만 React-Redux는 store 상태가 업데이트될 때마다 항상 전체 컴포넌트 트리에 대해 `mapState/useSelector`를 실행해야 한다. 대부분의 경우, 이러한 selector를 실행하는 비용이 React가 다른 렌더링 패스를 수행하는 비용보다 적기 때문에 일반적으로 이익이 발생하지만 이 작업은 반드시 수행되어야 하는 작업이다. 하지만 이러한 selector가 expensive한 변환을 수행하거나 새로운 값을 반환하지 않아야 할때 실수로 반환하는 경우 속도가 느려질 수 있다.


# Summary

- React는 기본적으로 항상 컴포넌트를 재귀적으로 렌더링하므로 부모가 렌더링될 때 자식도 렌더링된다.
- 렌더링 자체는 괜찮다. React가 어떤 DOM 변경이 필요한지 파악하는 방식이기 때문이다.
- 하지만 렌더링에는 시간이 걸리고 UI 출력이 변경되지 않는 "낭비된 렌더링"이 추가될 수 있다.
- 대부분의 경우 callback 함수나 객체같은 새 참조를 전달해도 괜찮다.
- `React.memo()`와 같은 API는 props가 변경되지 않는 경우 불필요한 렌더링을 건너뛸 수 있다.
- 하지만 항상 새로운 참조를 props로 전달한는 경우 `React.memo()`는 렌더링을 건너뛸 수 없으므로 해당 값을 memoize 해야할 수도 있다.
- context는 관심있는 깊게 중첩된 컴포넌트에서 접근할 수 있게 해준다.
- context provider는 value by reference로 값을 비교하여 값이 변경되었는지 확인한다.
- 새로운 context 값은 모든 중첩된 consumer를 리렌더링시킨다.
- 하지만 일반적인 부모 -> 자식 렌더링 폭포(cascade) 프로세스로 인해 자식 컴포넌트가 리렌더링되는 경우가 많다.
- 따라서 context 값을 업데이트할 때 전체 트리가 항상 렌더링되지 않도록 context provider의 자식을 `React.memo()`로 감싸거나 `{props.children}`을 사용할 수 있다.
- 자식 컴포넌트가 새로운 context 값을 기반으로 렌더링될 때 React는 거기서부터 cascading 렌더링을 계속한다.
- React-Redux는 context에 의해 상태 값을 전달하는 대신 Redux store에 대한 구독을 사용하여 업데이트를 확인한다.
- 이러한 구독은 모든 Redux store 업데이트에서 실행되므로 가능한 빨라야 한다.
- React-Redux는 데이터가 변경된 컴포넌트만 리렌더링하도록 하기 위해 많은 작업을 수행한다.
- connect는 `React.memo()`와 같은 역할을 하므로 연결된 컴포넌트가 많으면 한 번에 렌더링되는 컴포넌트의 수를 최소화할 수 있다.
- useSelector는 hook이므로 부모 컴포넌트에 의한 렌더링을 중지할 수 없다. useSelector만 있는 앱은 항상 렌더링이 cascading되는 것을 피하기 위해 일부 컴포넌트에 React.memo()를 추가해야 한다.
- "React Forgot" 자동 메모이징 컴파일러가 출시되면 이 모든 것이 대폭 간소화될 수 있따.
