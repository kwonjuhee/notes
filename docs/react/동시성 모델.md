	- `deadline.timeRemaining()` : 유휴 시간이 얼마나 남았는지 확인

### Scheduler Package 탄생

`requestIdleCallback`의 한계로 자체적인 스케줄러가 탄생하였다.

- 개념상 `requestIdleCallback`과 유사한 cooperative scheduling of background task 모델 사용
- 정확한 스케줄링 시간을 위해 MessageChannel API를 기반으로 5ms마다 메인 스레드를 양보하도록 함
- 작업 우선순위 지원 (Heap)

- heap의 정렬 기준은 expirationTime
- scheduleCallback 호출시 우선순위를 지정
- 우선순위에 따라 expirationTime이 결정된다.

## Fiber Architecture

컴포넌트를 순회하면서 메인 스레드를 블록하지 않을 방법

### Fiber란?

- Fiber는 렌더링 작업을 미세하게 분할한다.
- 자바스크립트 stack을 사용하지 않기 위해 작업을 힙 객체에 펼친 것
- 스택 프레임을 메모리에 유지하기 때문에 언제든지 실행 및 중지할 수 있다.
- algebraic effects를 지원하기 위한 기반이 된다.
- react 요소 -> Fiber -> UnitOfWork

### Double Buffering Model

> 버퍼에 쓰기, 읽기 속도 차이로 인해 불완전한 버퍼를 화면에 그릴 경우 발생하는 깜빡임 문제를 해결하기 위한 방법이다. front buffer를 화면에 출력하는 동안 back buffer에 다음에 그려질 내용을 쓰고, 쓸 내용이 다 채워지면 두 버퍼를 스위칭한다.

## 새로운 우선순위 모델 : Lane Model

말 그대로 차선의 개념이다. 32비트 데이터로 다수의 고유한 작업 스레드를 표현하며 우측에 가까운 비트일수록 우선순위가 높다.

업데이트의 종류에 따라서 Lane을 할당하고, reconciler가 현재 렌더링 대상인 lane 위에 올라가 있는 업데이트들을 배치 처리 한다.

![[동시성 모델-8.png]]

업데이트의 시작점은 DOM 이벤트일 수도 있고 비동기, 전환 이벤트일 수도 있다. 각 이벤트들은 다음과 같이 구분되어 하나의 lane에 대응된다.

- **SyncLane** : 사용자의 인터랙션에 의해 발생한 이벤트 중 개별적으로(discrete) 처리해야 하는 이벤트
	- click, input, mouse down, submit ...
- **InputContinuousLane** : 사용자의 인터랙션에 의해 발생한 이벤트 중 연속적으로(continuous) 발생하는 이벤트
	- drag, scroll, mouse move, wheel
- **DefaultLane** : 기타 모든 이벤트, React 외부에서 발생한 업데이트
	- setTimeout, 네트워크 요청 등
- **TransitionLane** : 개발자가 정의한 전환 이벤트
	- Suspense, useTransition, useDefferredValue를 통해 생성된 업데이트

### Lane 모델이 해결하고자 하는 것

#### ✔️ Suspense와 I/O Bound 개념의 등장으로 업데이트 구분이 필요해짐

>  expiration time 모델([[동시성 렌더링 (Concurrent Rendering)#Scheduler 우선순위 제어]])은 두 가지 개념이 하나의 시간 데이터에 존재했다.
>  - 우선순위 : 업데이트를 발생시킨 이벤트를 기준으로 우선순위를 결정하고 업데이트 간 우선순위는 대소 비교를 통해 판단
>  - 배치 여부 : 업데이트의 배치 여부는 값의 대소 비교를 통해 판단
> 
> Suspense가 나오기 전에는 우선순위가 아닌 다른 이유로 작업의 순서를 결정해야 할 이유가 없었다. 하지만 Suspense와 함께 렌더링에 I/O Bound라는 개념이 추가되면서 다른 방식이 필요하게 되었다.

일반적인 모든 렌더링 작업은 CPU Bound에 해당되고 네트워크 요청과 전환(transition)이 결합된 경우는 I/O Bound에 해당된다. I/O Bound를 처리하기 위해 Suspense를 사용했다면 렌더링 경로의 요소들이 모두 준비될 때까지 렌더링을 보류한다.

렌더링 작업이 I/O > CPU 순으로 진행될 경우 I/O Bound 렌더링이 CPU Bound 렌더링 작업을 차단하는 상황이 발생한다. I/O Bound는 CPU Bound보다 상대적으로 느릴 수 밖에 없고 사용자 또한 I/O Bound 작업이 즉각적일 것이라 기대하지 않기 때문에 같은 우선순위를 가진 작업이라도 I/O Bound보다는 CPU Bound를 먼저 처리하는 것이 유리하다.

(일반 업데이트와 Suspense의 조합은 항상 CPU Bound다. 이때의 Suspense는 하위 요소 중 하나라도 준비되지 않았다면 fallback으로 대체하여 렌더링을 마무리하기 때문에 네트워크에 의존적인 상태에서 렌더링을 이어가는 상황은 발생할 수 없으므로 이때의 렌더링은 항상 CPU Bound다.)



expiration time은 이벤트 우선순위와 업데이트 발생 시점을 기준으로 계산하기 때문에 같은 우선순위를 가지는 경우에 I/O - CPU 작업을 구분하거나 제거할 수 없다.

Lane 모델은 두 가지 개념(업데이트 간의 우선순위, 업데이트 배치 여부)을 분리하여 관리할 수 있도록 구상되어 기존 모델에서 발생할 수 있는 CPU 병목 현상을 해결할 수 있다.

I/O Bound 렌더링을 이어가는 중에 전환 업데이트가 추가로 발생하면 I/O Bound 렌더링의 Lanes를 `suspendedLanes`로 기록하고 CPU Bound의 전환 Lanes로 인터럽트되어 새로운 전환 업데이트 렌더링을 새로 시작한다.

같은 전환 업데이트라도 CPU와 IO를 나눌 수 있는 이유는 TransitionLane이 여러개이기 때문에 가능하다. expiration time과는 다르게 같은 우선순위를 가졌어도 업데이트를 다르게 배치 처리할 수 있는 것이다.



Task Prioritization : Lane Type
- 1순위 : 기한이 지난 또는 동기화 작업
- 2순위 : 사용자 상호 작용에 의한 업데이트
- 3순위 : 일반 우선순위 (네트워크 요청에 의해 생성된 업데이트 등)
- 가장 낮은 순위 : Suspense

Task Batching : Lanes Type
- InputDiscreteLanes : 사용자 상호 작용
- DefaultLanes : 데이터 요청에 의한 업데이트
- TransitionLanes : Suspense, useTransition, useDeferredValue

#### - 중간 상태 건너뛰기

자동완성 UI를 예로 들면, 사용자 입장에서 "리액" 입력이 완료된 시점에 "리"의 자동완성 UI에는 관심이 없을 것이다. 하지만 데이터 도착 순서대로 렌더링을 진행하게 되면 이미 "리액"의 데이터가 도착했을지라도 "리" 데이터의 렌더링을 먼저 진행하기 때문에 불필요한 렌더링이 발생한다.

React는 대규모 UI 전환 중이더라도 오래된 상태의 렌더링을 중단하고 최신 상태의 렌더링만 수행할 수 있다.

전환 업데이트 중에 우선순위가 더 높은 업데이트가 발생하면 reconciler는 진행중이던 전환 업데이트를 중단하고 Sync Lane의 업데이트를 먼저 처리한다. 그 후 Transition Lane의 업데이트들을 중간 상태의 렌더링을 진행하지 않고 배치 처리하여 한 번의 렌더링으로 마무리한다.

#### - 우선순위가 더 높은 업데이트 먼저 처리하기

업데이트 처리 방식은 git과 유사하다.

A라는 hook에 업데이트가 T1 - S2 - T3 순으로 발생했다고 가정해보자.

(main) T0
(feature) T1 - S2 - T3

업데이트 중 가장 먼저 처리해야할 것은 Sync Lane이다. S2를 cherry pick해서 main에 병합한다.

(main) T0 - S2
(feature) T1 - S2 - T3

다음으로 Transition Lane을 처리한다. 이때는 커밋의 순서를 맞추기 위해 rebase를 진행한다.

(main) T0 - T1 - S2 - T3
(feature) T1 - S2 - T3

모든 커밋이 병합되었으니 feature 브랜치를 삭제한다.

(main) AT0 - AT1 - AS2 - AT3
(feature)

우선순위에 따라 동일한 hook에서 업데이트 처리 순서가 달라질 경우 이런 rebase 과정이 추가로 필요하다. 우선순위에 따라 중간 상태는 다를 수 있지만 결국 마지막에는 rebase를 통해 업데이트 순서를 보장하므로 마지막 상태 값은 항상 사용자 상호 작용과 일치하게 된다.

만약 모든 업데이트가 같은 우선순위를 가졌다면 간단히 fast forward merge만 진행한다.

(main) AT0
(feature) AT1 - AT2 - AT3
->
(main) AT0 - AT1 - AT2 - AT3
(feature)
