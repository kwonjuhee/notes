## HTTP의 문제점

- TCP/IP는 도청 가능한 네트워크이므로 민감한 데이터를 평문으로 주고받는 것은 위험하다.
- 통신 상대를 확인하지 않기 때문에 위장이 가능하다.
  - 클라이언트가 보낸 요청에 대해 응답한 서버가 위장한 서버일 수 있다. 클라이언트는 이를 확인할 수 없다.
  - 응답을 받은 클라이언트가 위장한 클라이언트일 수 있다. 서버는 이를 확인할 수 없어 무조건 응답을 반환한다.
- 요청이나 응답이 수신 도중에 변조되었다 하더라도 변조 사실을 알 수 없다.
  - 중간자 공격 위험

## HTTPS

**💡 HTTP 프로토콜의 암호화된 버전 (HTTP Secure)**

- SSL(TLS) 프로토콜 위에서 동작
- 클라이언트와 서버의 통신 암호화
- 인증서를 통해 신뢰할 수 있는 상대인지 인증
- MAC 인증값을 통해 데이터 무결성과 인증 제공

> SSL과 TLS
> - SSL은 넷스케이프사가 내놓은 프로토콜로 SSL3.0까지 개발되었다.
> - 이후 IETF로 옮겨져 SSL3.0을 기반으로 한 TLS1.0
> - 총칭해서 SSL이라고 부름

## SSL 암호화 방식

기본적으로 key(uniformly distributed random string)을 이용하여 메시지를 암호화한다.

### 대칭키 암호 시스템

- 서로 공유된 비밀키를 이용하여 암호화, 복호화한다.
- 암호문이 네트워크(insecure channel)를 통해 전송된다.

> 🚨 안전하게 키를 공유할 수 있는 방법이 필요
> - 키가 유출되면 공격자가 암호를 복호화할 수 있다.
> - 근데 애초에 키를 안전하게 보낼 수 있다면 데이터도 안전하게 보낼 수 있다.

### 공개키 암호 시스템

- 각 사람마다 한쌍의 키 보유
  - **공개키 pk** - 모두에게 공개 / **개인키 sk** - 비밀로 보관
- 공개키 집합에서 받아온 **상대방의 공개키를 통해 암호화**하여 전송
- 수신자는 **자신의 개인키를 이용하여 암호문을 복호화**
- 개인키를 통신으로 보낼 필요가 없다.
- 공개키를 통해 복화할 수 없고 개인키를 도출하는 것 또한 불가능

> 🚨 대칭키 방식에 비해 처리 속도가 늦다.

### 하이브리드 암호 시스템 (💡SSL 방식)

- 키를 교환할 때 공개키 방식을 사용하고, 그 후 통신은 대칭키 방식을 사용
- 공개키 방식의 처리 속도 문제를 보완

1. 공개키 암호 시스템을 통해 대칭키를 상대방의 공개키로 암호화하여 공유한다.
2. 대칭키를 이용하여 데이터를 암호화한다.
3. 암호화된 대칭키와 암호문을 전송한다.
4. 수신자는 자신의 개인키로 암호화된 대칭키를 복호화한다.
5. 복호화한 대칭키를 이용하여 암호문을 복호화한다.

> 🚨 수신한 공개키를 신뢰할 수 없는 문제가 발생한다.
> - 공개된 공간 (cloud) 에 공개키를 선언하게 되면 신뢰성 문제 발생
> - 신뢰할 수 있는 서버를 이용하게 되면 서버에 과부하 문제 발생
> 
> => 인증서를 p2p로 전달하여 해결

## SSL 인증서

- SSL 통신에 사용하기 위한 **공개키를 클라이언트가 검증**하기 위함. 검증된 공개키는 **신뢰할 수 있는 서버임을 보장**한다.
- 인증서는 클라이언트와 서버가 모두 신뢰하는 제 3자 기관인 **인증 기관(CA, Certificate Authority)에 의해 발행**된다.

### 전자 서명

- 개인키를 서명할 때 사용하고 서명을 검증할때 공개키를 사용한다.
  1. 키 생성 과정을 통해 공개키 pk, 개인키 sk를 생성한다.
  2. $s = Sig_{sk} (m)$ 자신의 개인키 sk를 이용하여 m에 대한 서명을 생성한다.
  3. 메시지와 전자서명 전송
  4. $Ver_{pk}(m,s)$ 송신자의 공개키로 검증한다.

- 데이터를 보호하는 목적이 아니라 **인증서의 무결성을 보장해주는 용도**로 사용된다.
  - 공개키와 쌍을 이루는 개인키로 암호화되었다는 것을 의미

- 공개키는 암호화 속도가 느리기 때문에 해쉬 값에 서명하는 방식으로 속도를 개선할 수 있다.
  - $s =Sig_{sk}(h(m))$
  - 해쉬 함수는 고정된 길이의 출력 값을 가지므로 데이터의 크기가 클 때 성능을 개선할 수 있다.

### 인증서를 이용한 공개키 인증 과정

1. CA에 공개키 인증서를 요청한다.
2. CA는 요청받은 공개키를 CA의 개인키로 전자서명하여 인증서를 발급한다.
3. 수신자는 CA의 공개키를 이용하여 인증서의 손도장(CA의 전자서명 값)을 검증한다.
3. 수신자는 OCSP 프로토콜을 통한 인증서의 폐기여부 또한 확인한다.

**💡 CA의 공개키로 인증서의 손도장(CA의 전자서명 값)을 검증하는 공개키 암호 시스템 방식**
- 인증서 검증은 곧 서버의 공개키 또한 검증되는 것 (인증서에 주체와 공개키가 기록되어 있으므로)
- 전자서명을 검증하는 것을 통해 인증서의 무결성 또한 검증된다.
- CA의 공개키 또한 클라이언트에 안전하게 전달되어야 하기 떄문에 브라우저에 사전 내장되어있다.

### 인증서 형태

- 인증서에는 서비스 정보(인증서를 발급한 CA, 서비스의 도메인 등)와 공개키가 담겨있다. 
- 인증서 내용을 암호학적 해쉬함수를 통해 해쉬 값을 생성하고 해쉬 값에 CA의 개인키로 서명을 한다. => 전자서명
- 이렇게 생성된 전자서명은 인증서에 인증 태그로 포함된다.

### PKI 인증 기관들 간 신뢰 모델

- 국내 모델 - 계층 모델
  - 상위 계층이 바로 아래 계층의 인증서를 발급
  - 최상위 계층인 루트 인증 기관은 self-signing
  - ROOT 인증 기관은 KISA한국인터넷진흥원

- 국가간 상호인증 - 메쉬 모델
  - 각 국가의 루트 인증 기관은 신뢰

## SSL handshake protocol

<img src="https://user-images.githubusercontent.com/62097867/231418585-cfd266b5-88de-4f4b-837f-9659b28ba2da.png" width="500px" />

1. 클라이언트가 서버에 Client Hello 메시지를 송신한다.
   - 클라이언트가 제공하는 SSL/TLS 버전 정보
   - 클라이언트가 지원하는 Cipher Suite (사용 가능한 암호화 유형 등)
   - 클라이언트가 생성한 난수

2. 서버가 SSL 통신이 가능하다면 Server Hello 메시지로 응답한다.
   - 클라이언트의 Cipher Suite 중 선택
   - 서버의 공개키가 담긴 SSL 인증서
   - 서버가 생성한 난수

3. 클라이언트가 서버 인증서를 검증한다.
   - CA의 공개키로 복호화하여 신뢰할 수 있는 서버임을 확인
   - 인증서에 담긴 서버 공개키 획득

4. Key Exchange
   - 클라이언트가 이전에 생성한 난수들을 이용해 pre-master key를 생성한다.
   - 서버의 공개키로 암호화하여 서버에 전송한다.
   - 서버는 이를 받아서 개인키로 복호화한다.
   - 이 값을 통해 session key를 생성하여 클라이언트와 공유한다.

6. Finished
   - SSL 연결이 확립되고 키가 교환되었으므로 이제부터 암호화 통신
   - session key를 통해 대칭키 방식으로 암호화하여 통신한다.

## SSL record protocol

<img src="https://user-images.githubusercontent.com/62097867/231449044-11a4d32f-7ff9-4dc2-ad57-c161083edae4.png" width="500px" />

- 데이터를 단편화하고 압축한다.
- 압축된 데이터를 세션키로 hash하여 MAC 인증 값 생성
  - MAC(Message Authentication Code)은 데이터 무결성, 인증을 제공
- 압축된 데이터(평문) + MAC을 대칭키 암호화

=> 최종적으로 암호화 + 인증된 SSL 패킷 생성

결론 인증서를 통해 공개키를 검증하고 검증된 공개키를 통해 세션키를 만들어서 공유한 후 세션키를 통해 암호화된 통신을 한다.
